# 餐厅排序

## 何时读取

只由 `restaurant_ranking` 阶段读取。前提是 discovery 与 route evaluation 均完整提交，且两者候选集合完全一致。

## 输入边界

- 可以读取门店旅行价值、运营快照、路线评估、餐窗意图与用户约束。
- 不得创建新餐厅、替换分店、删除不喜欢的候选或修改上游事实。
- 发现候选已闭店或严重不适用时，退回 discovery 更新集合，再重新执行路线评估与排序。

## 决策原则

- `destination`：优先独特性和旅行价值，再验证重排后是否可执行。
- `experience`：平衡旅行价值、路线成本、偏好和运营稳定性。
- `convenience`：优先顺路、出餐速度、营业稳定和下一硬时间。
- 赶车、长途驾驶、高海拔、老人儿童或晚到场景，提高执行稳定性权重。
- 缺少评价量的评分只能作为平台展示值，不能据此宣称“口碑最佳”。

## 结构化产出

每个 `meal_options[]` 至少包含：

- 与上游一致的 `candidate_ids[]`；
- 连续且不重复的候选 rank；
- `selected_candidate_id` 与一个或多个 `fallback_candidate_ids[]`；
- 每个候选对应的 snapshot 与 route evaluation 引用；
- 选择理由、切换条件、前后锚点、时间窗和 candidate policy。

内部权重、评分拆解和研究过程不进入旅行者页面。

## 完成门槛

- 主选 rank 为 1，备选不重复且都来自同一候选集。
- 正常餐窗至少有一个结构化备选。
- 主选失效条件能明确触发某个备选，而非“附近再找”。
- 时间窗与日程事件一致，变化时重新核验运营与路线。
