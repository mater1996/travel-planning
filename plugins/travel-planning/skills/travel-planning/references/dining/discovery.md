# 餐厅发现与旅行价值

## 何时读取

仅由 `restaurant_discovery` 阶段读取。前提是正式餐窗、前后锚点、交通方式、绕行上限和人群约束已经明确。

## 输入

- `meal_id`、日期、餐别、时间窗和 `meal_intent`。
- `previous_anchor` 与 `next_anchor` 的名称、具体地址和坐标。
- 预算、人数、饮食限制、停车等约束与搜索范围。
- 路线前轻量预研提取的地方美食主题，但它只能作为发现线索。

## 发现流程

1. 从近期独立社区原帖、地方专题或用户明确偏好中形成门店线索。
2. 用地图或官方页面解析到具体分店，核验规范名称、POI、地址和坐标。
3. 合并同一门店别名，排除已闭店、搬迁、只存在于榜单摘要或无法定位的条目。
4. 保存菜系、特色菜、预算、份量、服务、排队、适合人群和推广风险。
5. 将平台评分、评价量、社区体验和官方菜单分开，不计算无来源综合分。
6. 判断 `route_worthy`：这家门店是否值得主 Agent 改变当日事件顺序或交通骨架。

## 社区证据规则

- `route_worthy=true` 至少需要两条近期、相互独立、能定位具体分店的社区来源。
- 社区内容支持口味、份量、排队、环境与避坑；不能单独证明营业、价格、预约或食品安全。
- 明显营销、搬运、仅有合集摘要或时间过旧的内容降低权重并记录风险。

## 结构化产出

- `restaurants[]`：稳定门店身份、位置、菜系、特色菜和静态来源。
- `restaurant_snapshots[]`：适用餐窗的运营与平台动态覆盖。
- `meal_candidate_sets[]`：每餐候选 ID、候选策略、前后锚点、约束和路线影响。
- 每个候选的 `value_assessment={status, route_worthy, summary, source_ids}`。

本阶段不得输出最终 `meal_options[]`，也不得提前决定主选。

## 完成门槛

- 正常餐窗有 2 至 3 个去重、可定位、与预算饮食约束兼容的候选。
- 每个候选同时存在餐厅实体和匹配的动态快照。
- 前后锚点完整且搜索数量不小于候选数量。
- `route_influence` 完整对应所有 route-worthy 候选；需要重排时等待主 Agent处理后再做路线评估。
