# 餐厅路线评估

## 何时读取

只由 `meal_route_evaluation` 阶段读取。必须依赖已经完整提交的 discovery；如有 `route_worthy` 候选，主 Agent应先决定是否重排当日路线。

## 比较原则

每个餐窗先计算唯一直接基准：上一锚点直接到下一锚点。随后对 discovery 的每个候选计算：

```text
上一锚点 → 餐厅 → 下一锚点
```

所有候选使用相同交通方式、路线策略、出发时刻和门到门口径，避免一个按车上时间、另一个按完整步行等待时间。

## 输入

- discovery 的完整候选 ID 集合、具体分店地址与坐标。
- 前后锚点的名称、具体地址、坐标。
- 餐窗交通方式、出发时刻、路线策略与最大绕行分钟。
- 主 Agent重排后的最新锚点；锚点变化时不得复用旧评估。

## 结构化产出

- 每餐恰好一个 `meal_baseline_routes[]`，包含起终锚点、交通方式、策略、出发时刻、门到门分钟、地图链接、查询时间和来源。
- 每个候选恰好一个 `meal_route_evaluations[]`。
- 评估包含 `from_previous`、`to_next` 两腿的端点、距离、路线耗时、门到门耗时和地图链接。
- `total_door_to_door_minutes` 等于两腿之和；`detour_minutes` 等于总耗时减基准耗时。
- 主选确定后，`from_previous` 与 `to_next` 中实际执行的腿必须物化为 `transport_edges[]` 并进入逐日时间轴；候选卡内路线不能代替正式交通事件。

## 校验

- 评估集合必须与 discovery 候选集合完全一致，不能遗漏或增加候选。
- 两腿端点必须和 discovery 的锚点、餐厅实体一致。
- 超出原最大绕行但 `route_worthy=true` 的候选，不能直接淘汰；先交回主 Agent决定是否重排，再重新计算。

## 完成门槛

- 每餐有且只有一个统一基准。
- 所有候选同口径覆盖且计算可复核。
- 路线链接能定位真实端点，不使用“上一站/下一站”占位。
- 主选的进店和离店路线已交给主 Agent形成相邻交通事件；若下一锚点是当晚住宿，离店路线必须闭合到该住宿。
- 数据变化后重新计算，不把旧地图结果当当前事实。
