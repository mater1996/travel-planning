# 领域研究分类

本文定义各研究模块的职责、触发条件和完成结果。字段名是目标设计建议，最终实现时仍需与 schema、模板和审查器一起评审。

## 1. 交通研究

### 1.1 `transport.core`

任何实际移动边都必须加载，统一回答：

- 从哪个准确出口或上车点，到哪个准确入口或下车点；
- 交通方式、线路或班次，以及采用理由；
- 步行、等待、换乘、安检、取行李和缓冲后的门到门时间；
- 按人或按车的费用口径、动态状态和查询时间；
- 行李去向、首末班、停止入场和下一硬时间约束；
- 主方案失败时的可执行备选及切换条件；
- 官方、运营方、平台、地图、社区和估算分别支持哪些事实。

基础模块不规定具体方式的专用字段。所有动态价格和库存继续使用快照与具体 offer 绑定。

### 1.2 `transport.flight`

触发条件：任一候选或采用交通为航班。

额外研究：

- 出发与到达机场全名、航站楼、当地日期、当地时间和时区；
- 航班号、承运与实际执飞、经停、含税价格口径；
- 手提与托运行李，额外行李费用和联程行李规则；
- 值机、安检、边检、机场内移动和到达后取行李缓冲；
- 机场往返住宿或首末景点的地面接驳；
- 分开出票、自行中转、跨机场和重新托运风险；
- 退改、延误或取消时的备选；
- 平台候选、运行状态与最终出票状态严格分离。

### 1.3 `transport.rail`

触发条件：任一候选或采用交通为铁路、高铁、城际铁路或夜行列车。

额外研究：

- 准确出发站和到达站，不能只写城市；
- 车次、席别、运行日、出发到达时间与跨日关系；
- 开售时间、实名证件、检票停止时间和进站缓冲；
- 行李规则、大站换乘、同站或跨站换乘；
- 到站后的末班交通和夜间接驳；
- 中国铁路平台候选与 12306 最终复核状态；
- 无票、候补失败、停运或晚点时的替代交通。

### 1.4 `transport.public_transit`

触发条件：采用公交、地铁、有轨电车、公共轮渡或官方接驳。

额外研究：

- 准确线路、方向、上下车站和换乘站；
- 首末班、运营日、购票方式和行李限制；
- 站内步行、无障碍路径、出口选择和出站到目的地入口；
- 大件行李、老人儿童、夜间和拥挤时的替代方式。

### 1.5 `transport.self_drive`

触发条件：旅行者驾驶自有车或租赁车辆完成任一主要交通边。

额外研究：

- 车辆类型、能源类型、实际驾驶员和可驾驶时段；
- 驾驶资格、当地交通规则、限行、通行证和区域管制；
- 道路等级、收费、服务区、山路、冬季路况和临时封路；
- 连续驾驶时间、换驾、休息点、夜驾和疲劳风险；
- 油量或电量基线、加油或充电位置、补能时间和失败备选；
- 每个停靠点的停车场、入口、营业时间、费用、容量风险；
- 停车点到景点入口、餐厅或酒店的步行路线；
- 事故、故障、爆胎、恶劣天气和道路关闭的应急联系与降级。

自驾的完成门槛不能只有高德 `car` 路线。至少要覆盖车辆生命周期、驾驶约束、停车和补能。

### 1.6 `transport.car_rental`

触发条件：自驾车辆需要租赁。它依赖 `transport.self_drive`，不能单独代表交通执行方式。

额外研究：

- 取车与还车门店、准确地址、营业时间和航班或车次衔接；
- 主驾驶和附加驾驶员的证件、驾龄、年龄和信用要求；
- 车型组、座位、行李容量、能源类型和替代车型规则；
- 租金、押金、预授权、保险、免赔额和道路救援；
- 里程限制、油量或电量政策、清洁费和超时费；
- 异地还车、跨区域或跨境限制；
- 取车验车、损伤记录、设备检查和还车留痕；
- 儿童座椅、冬季装备、取消和未到店规则。

### 1.7 `transport.charter_driver`

触发条件：采用包车加司机或司导。

额外研究：

- 车辆、座位、行李容量和司机资质；
- 服务日期、时长、上下车点和每日里程；
- 报价按车或按人，包含与排除项目；
- 油费、路桥、停车、司机食宿、异地返空和超时；
- 保险、合同、退改、司机更换和紧急联系状态；
- 是否允许途中改变停靠点，以及变化后的计价方式。

### 1.8 `transport.coach_ferry`

触发条件：采用长途大巴、客运船、公共渡轮或岛际船班。

额外研究：

- 客运站、码头、承运方和准确上下车船点；
- 班次、开售、实名、行李、检票和停止登乘；
- 天气、潮汐、季节停航和替代路线；
- 晚到后的末班接驳和过夜方案。

## 2. 景点研究

### 2.1 `attractions.core`

所有进入候选集的景点统一研究：

- 规范名称、实体地址、坐标、官方主页、公告和预约入口；
- 适用日期的开放、停票、停止入场、闭园和临时公告；
- 当季看点、最佳时段、普通游览时长和采用理由；
- 推荐入口、入口选择理由、建议出口和最晚离开时间；
- 从入口到出口的结构化 checkpoints、内部移动和失败备选；
- 基础门票、必选景交、可选体验和互斥套票；
- 预约产品、人数、场次、放票规则、截止和无票备选；
- 体力、天气、无障碍、行李和下一段交通约束；
- 官方事实、近期体验和图片授权分别来自哪里。

社区内容只能支持体验、拥挤、玩法和避坑，不能单独证明开放、价格、资质或安全。

### 2.2 景点类型 Profiles

| Profile | 触发条件 | 额外研究重点 |
| --- | --- | --- |
| `attractions.museum_venue` | 博物馆、美术馆、展馆、室内场馆 | 闭馆日、预约时段、证件、安检、寄存、展厅顺序、临展与常设展 |
| `attractions.scenic_area` | 大型景区或多入口景区 | 入口选择、景交、索道/观光车、内部换乘、分区开放、出口衔接 |
| `attractions.mountain_outdoor` | 山岳、徒步、峡谷、雪地、高海拔 | 步道等级、爬升、日落、天气、地灾、索道停运、最晚下撤、装备和救援 |
| `attractions.theme_park` | 主题乐园、水乐园、大型游乐园 | 开园策略、项目限制、排队、预约通行、演出时刻、闭园疏散和园内餐饮 |
| `attractions.performance_night` | 演出、夜游、灯光秀、夜景 | 固定场次、入场、散场、夜间交通、天气取消、座位或观景位置 |
| `attractions.neighborhood_walk` | 街区、古镇、商圈、城市漫步 | 合理起终点、营业分布、可跳过节点、夜间安全、卫生间和补给 |

一个景点可同时激活多个 profile，例如夜间山岳活动同时激活 `mountain_outdoor` 和 `performance_night`。

## 3. 餐饮研究

餐饮保留现有三阶段依赖，但将规则按职责拆开。

### 3.1 `dining.core`

任何正式午餐或晚餐都需要：

- 餐别、日期、时间窗和用餐时长；
- 上一锚点与下一锚点的名称、具体地址和坐标；
- `destination`、`experience` 或 `convenience` 用餐意图；
- 人数、预算、忌口、过敏、儿童、老人和停车等约束；
- 正常场景 2 至 3 个实体候选，受限场景有搜索范围和应急补给；
- 主选、结构化备选和切换条件。

### 3.2 `dining.discovery`

负责回答“这家店本身是否值得去”：

- 具体分店身份、POI、地址、坐标和去重；
- 菜系、特色菜、饮食标签和预算适配；
- 近期独立社区原帖支持的口味、份量、服务、排队和推广风险；
- 城市美食主题是否能由具体门店菜单或可靠字段证明；
- 是否 `route_worthy`，以及是否需要主 Agent 重排路线；
- 平台评分与社区信号分开保存，不合成无来源总分。

### 3.3 `dining.operations`

负责日期与餐窗内的可执行性：

- 营业时间、午晚市、临休和节假日覆盖；
- 预约方式、排队、取号、菜单、人均和复核时间；
- 停车、上下客、无障碍、包间和大桌；
- 官方、商家、平台和地图分别支持的字段；
- 动态字段不可得时的查询入口和下一次复核时间。

### 3.4 `dining.route_evaluation`

负责同口径比较：

- 每餐唯一的直接基准路线；
- 上一锚点到餐厅、餐厅到下一锚点的两腿路线；
- 相同交通方式、路线策略和出发时刻；
- 距离、门到门时间、基准时间和额外绕行；
- `route_worthy` 超出原绕行上限时先重排，再重新计算。

### 3.5 `dining.ranking`

只读取 discovery 与 route evaluation 的完整候选集合，不创建新候选：

- `destination` 优先旅行价值，再检查重排后能否执行；
- `experience` 平衡门店价值、路线、偏好和运营稳定性；
- `convenience` 优先顺路、出餐和营业稳定性；
- 赶车、高海拔、长途驾驶和晚到提高执行稳定性权重；
- 输出主选、备选、连续排名和切换条件，但不向旅行者展示内部打分。

### 3.6 餐饮场景 Profiles

| Profile | 触发条件 | 额外要求 |
| --- | --- | --- |
| `dining.driving_parking` | 前后交通为自驾或包车 | 停车场、上下客点、停车费、停车后步行和酒精饮品风险 |
| `dining.dietary_allergy` | 有忌口或过敏 | 菜品成分、交叉污染可核验范围、沟通方式和安全备选 |
| `dining.large_group` | 大团体或需要同桌 | 容量、包间、大桌、预订、最低消费和分桌备选 |
| `dining.constrained_venue` | 机场安检区、封闭景区、服务区或深夜 | 搜索边界、唯一候选证据、便利店/自备食物和下一可用餐点 |

## 4. 住宿研究

### 4.1 `lodging.core`

- 酒店或住宿实体的全名、城市、行政区、地址和坐标；
- 入住与退房日期、连续入住夜、人数、房间、床型；
- 价格口径、税费、早餐、取消和支付条件；
- 多间同房型库存是否由供应商查询能力支持；
- 入住证件、前台时段、凌晨入住和行李寄存；
- 到主要交通枢纽、首景点和末景点的门到门路线；
- 采用的报价候选绑定具体快照和 offer。

### 4.2 住宿场景 Profiles

| Profile | 触发条件 | 额外要求 |
| --- | --- | --- |
| `lodging.multi_room` | 两间及以上房间 | 同房型容量、房间数量、分房规则和库存口径 |
| `lodging.late_arrival` | 深夜或凌晨入住 | 前台时段、保留房、接驳、无人值守和失败备选 |
| `lodging.self_drive` | 自驾入住 | 停车入口、住客停车费、车位风险、限高和充电设施 |
| `lodging.resort_remote` | 度假村或偏远住宿 | 接驳、餐饮依赖、补给、封路和取消后的替代住宿 |

餐窗创建应从 `stay-food` 中独立为 `meal-windows` 决策或由主 Agent 根据事件骨架生成，避免住宿 Agent 同时拥有餐厅决策。

## 5. 横切场景

横切 profile 不拥有主要实体，只向已有任务增加约束和完成门槛：

- `scenario.children`：儿童座椅、身高年龄限制、推车、休息与就餐。
- `scenario.elderly`：步行、爬升、换乘、卫生间、休息与医疗可达性。
- `scenario.accessibility`：无障碍入口、电梯、站内路径、客房与预约协助。
- `scenario.large_luggage`：站场、车辆、寄存和退房到入住的连续行李路径。
- `scenario.cross_border`：签证、过境、证件、保险、通信和货币。
- `scenario.severe_weather`：高温、暴雨、降雪、台风、地灾及路线降级。

横切 profile 应绑定到具体事件、交通边、景点或 checkpoint，不能只生成泛化提醒。

## 6. 字段所有权建议

| 任务域 | 独占产出 | 只读依赖 |
| --- | --- | --- |
| `attractions` | 景点实体、运营、入口出口、checkpoints、费用、预约草案 | 路线日期、人群和天气约束 |
| `transport-intercity` | 城际候选、库存引用、跨城门到门比较 | 城市顺序、住宿日期、硬时间 |
| `transport-local` | 本地交通边、路线锚点 | 景点入口出口、住宿和餐饮锚点 |
| `road-trip` | 车辆、驾驶、租车、补能、停车生命周期 | 所有采用停靠点和日期 |
| `lodging` | 住宿实体、报价引用、入住与行李补丁 | 每日片区和交通窗口 |
| `meal-windows` | 餐窗、前后锚点、预算和饮食约束 | 初始事件骨架 |
| `restaurant-discovery` | 餐厅实体、动态快照和候选集合 | 餐窗和路线背景 |
| `meal-route-evaluation` | 基准与双腿路线 | 餐厅候选集合和更新后锚点 |
| `restaurant-ranking` | 最终 meal options | discovery 与路线评估 |
| `weather-risk` | 天气对象及事件影响 | 景点、交通和 checkpoint ID |

主 Agent 继续独占城市顺序、最终采用决策、事件排序、冲突裁决和最终页面。
